# Leela: производство и очереди Buffer

Состояние: код планировщика и Buffer-адаптера добавлен; живая интеграция ещё не проверена с аккаунтами. Для запуска выбрана только Maya; Alex и Zoe сохранены отключёнными. Для Maya пока не заполнены настройки Buffer; автоматический запуск не активирован. Push запускает только тесты и просмотр плана, без платной генерации и публикаций.

## Где что хранится

- `config/production.json`: персонажи Maya, Alex, Zoe, их внешность, голос, привязки каналов, параметры цикла. Это редактируемые JSON-данные в Git, отдельной БД пока нет.
- `config/phrases-en.json`: 60 английских вопросов, по 20 на тему персонажа, короткие мысли/реакции/CTA. Все произносят только «No way!».
- Приватный R2: `content-factory/production/v1/ledger.json` — постоянный журнал задач, использования фраз и независимых доставок YouTube/TikTok/Instagram. Каждый ролик сохраняет снимок своей конфигурации; изменение JSON не меняет уже запланированные задания.
- Приватный R2: исходник целиком, актёрские клипы, готовые видео, контрольные суммы и checkpoints генератора.
- Отдельный публичный R2 bucket: только готовые MP4 под случайными именами, с постоянными HTTPS-ссылками для Buffer. Приватный основной bucket не открывать.

## Персонажи и формат

| ID | Персонаж | Тема | Голос |
| --- | --- | --- | --- |
| maya | 30 лет, тёмные волосы, бежевый свитер | Overthinking | Jenny |
| alex | 32 года, короткие волосы, тёмно-синяя футболка | Direction | Guy |
| zoe | 27 лет, рыжие кудри, зелёный свитер | Boundaries | Aria |

Внешность пока описана текстом; портреты ещё не генерировались. При первом запуске создаётся один восьмисекундный актёрский фрагмент на персонажа, затем он повторно используется. Меняются вопросы и текстовые реакции; для разнообразия актёрских движений позже можно расширить банк клипов. Новое лицо на каждый ролик не генерируется. Фразы выбираются по минимальному числу использований, затем пул повторяется.

Формат: 3 секунды актёра → вся игровая запись на скорости 2.5× и 2 секунды финального кадра → 4 секунды реакции. Музыка непрерывная. Текстовые мысли остаются; углового водяного знака нет. Описание строго `Find on Telegram: @leela_ru_bot`. Параметры AI-disclosure передаются в служебных полях платформ, не добавляются в видеоряд или описание.

## Цикл

1. GitHub Actions просыпается ежедневно в 05:17 UTC. Публикации идут по расписанию Buffer, независимо от времени запуска Actions.
2. Проверяется доступность каналов, совпадение платформ, часовой пояс и два слота каждый день.
3. Читаются все страницы очередей и сверяются ранее сохранённые post ID. Внешние посты тоже занимают места.
4. Если наступил четвёртый календарный день после прошлого планирования (даты UTC), резервируются задания: первая партия до 10 на персонажа, далее пополнение до 10 с учётом очередей и незагруженного запаса. При двух публикациях в день обычно нужно 8 новых видео через 4 дня. Генерация строго 10 каждые 4 дня давала бы постоянно растущий остаток.
5. Незавершённая генерация продолжается с прежними ID и checkpoint. Готовые ролики повторно не генерируются.
6. Перед каждой отправкой проверяется ёмкость соответствующей очереди. Один ролик получает три независимых записи доставки. Не вместившиеся сохраняются для следующего прохода.
7. Buffer получает `automatic` + `addToQueue` и сам назначает следующий слот. YouTube — public, Instagram — reel.

Не используем cron `*/4` для дня месяца: это не равномерные 96 часов. Отсчёт привязан к началу даты UTC: небольшое изменение времени старта не переносит партию на пятый день. GitHub Actions может задержать или пропустить запуск. Сбой одного персонажа не останавливает обработку остальных. При накоплении 10 неотправленных роликов на одной площадке новые партии персонажа приостанавливаются, чтобы не раздувать запас.

## Что настроить перед первым запуском

1. Использовать один Buffer-аккаунт для Maya и подключить к нему по одному аккаунту YouTube, TikTok и Instagram. Для Instagram использовать аккаунт с автоматической публикацией Reels. Проверить автоматическую публикацию на каждой площадке.
2. Создать API key одного Buffer-аккаунта. Сохранить в GitHub Actions Secrets: `BUFFER_MAYA_API_KEY`. Ключи Alex и Zoe пока не нужны. Значения не присылать в чат и не коммитить.
3. Записать `organization_id` и три channel ID в конфигурацию Maya. Эти ID не являются секретами. В API Explorer можно запросить `account { organizations { id name } }`, затем `channels(input: {organizationId: "..."}) { id name service }`.
4. Выбрать IANA-часовой пояс целевой аудитории и записать `posting_timezone`. Пока `null`: местоположение владельца не определяет аудиторию. В каждом Buffer-канале выставить тот же пояс и слоты 09:00/19:00 ежедневно либо изменить оба слота в конфигурации.
5. Создать отдельный R2 bucket для опубликованных медиа, подключить постоянный публичный HTTPS-домен. Текущему R2 ключу дать доступ на запись в этот bucket. GitHub Actions Variables: `BUFFER_MEDIA_BUCKET` и `BUFFER_MEDIA_BASE_URL`. Основные R2 Secrets уже используются текущим генератором.
6. Maya уже выбрана (`enabled: true`), остальные отключены. Временно поставить `queue_target: 1`, `max_new_per_cycle: 1`; запустить workflow вручную с `execute: true`. Проверить реальное появление и публикацию на трёх площадках. Это необходимый живой тест, который ещё не проведён.
7. Вернуть target и cap к 10. Оставить только Maya; Alex и Zoe пока не включать. Установить Actions Variable `PRODUCTION_ENABLED=true`. Это включает выполнение по расписанию; до этого ежедневный workflow делает только тесты и preview.

Публичные MP4 автоматически не удаляются: ссылка должна работать вплоть до публикации, включая задержки очереди. Политику очистки можно добавить после подтверждения `sent` на всех трёх площадках. Доступ через короткоживущие подписанные ссылки здесь не используется.

## Восстановление

- Статус доставки `unknown` означает, что запрос мог дойти до Buffer, но подтверждение не сохранено. Автоматическая повторная отправка запрещена. Найти соответствующий ролик в Buffer по видео/времени, сохранить его post ID и статус `scheduled` в приватном журнале. Только после подтверждённого отсутствия поста вернуть `waiting`. Не сбрасывать журнал целиком.
- Ошибка существующего поста: исправить его в Buffer; следующий проход повторно читает тот же ID. Не создавать замену автоматически.
- Оставшаяся `lock.json`: сначала проверить отсутствие работающего workflow/платного запроса, затем разбирать checkpoint. Автоматического захвата старой блокировки нет.
- Ключи, тела ответов с медиа и публичные адреса видео не печатаются в публичных Actions-логах.
- Бесплатный Buffer API имеет собственные лимиты. Адаптер ограничивает вызовы одного прохода; при отказе API журнал остаётся целым, автоматического повтора POST нет.

## Проверка без внешних вызовов

```sh
python -m unittest discover -s tests -p test_production.py -v
python production.py
```

Тесты проверяют остаток 2 + пополнение 8, повторный запуск, переход месяца, полный канал, сохранение запаса, пагинацию и неопределённый исход отправки. Они не заменяют живую проверку авторизации и публикации Buffer.

Официальные источники API: https://developers.buffer.com/reference.html и https://developers.buffer.com/examples/create-video-post.html. Тариф: https://buffer.com/pricing.
